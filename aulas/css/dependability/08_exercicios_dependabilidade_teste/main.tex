\questao[10]{1} Marque a alternativa que descreve corretamente a cadeia \textit{fault} $\rightarrow$ \textit{error} $\rightarrow$ \textit{failure}:
\begin{enumerate}[label=(\Alph*)]
  \item Um \textit{fault} é sempre detectável imediatamente; um \textit{error} é o estado incorreto resultante; uma \textit{failure} é o defeito presente no código-fonte.
  \item Um \textit{fault} é um defeito latente no sistema; um \textit{error} é um estado incorreto ativado pelo \textit{fault}; uma \textit{failure} ocorre quando o \textit{error} compromete o serviço entregue ao usuário.
  \item Uma \textit{failure} precede o \textit{error}, que por sua vez ativa o \textit{fault} durante a execução.
  \item \textit{Fault} e \textit{failure} são sinônimos; \textit{error} é o mecanismo de detecção utilizado para identificá-los em tempo de execução.
\end{enumerate}

\ifgabarito
\begin{tcolorbox}[gabarito]
Alternativa \textbf{(B)}. O \textit{fault} é latente; é ativado e gera um \textit{error} (estado interno incorreto); o \textit{error} pode ou não propagar-se até uma \textit{failure} (serviço incorreto observável). As demais alternativas invertem a ordem ou confundem os conceitos.
\end{tcolorbox}
\fi

\vspace{8pt}

\questao[8]{2}
Considere o seguinte cenário: um microsserviço de pagamentos processa uma requisição de débito, mas um bug faz com que o saldo seja decrementado duas vezes quando ocorre um timeout seguido de retry pelo cliente.
\begin{enumerate}[label=\alph*)]
  \item Identifique o \textit{fault}, o \textit{error} e a \textit{failure} neste cenário.
  \item Proponha um mecanismo para evitar o problema (idempotência, deduplicação ou outro).
\end{enumerate}

\ifgabarito
\begin{tcolorbox}[gabarito]
\begin{enumerate}[label=\alph*),nosep]
  \item \textit{Fault}: bug que não garante idempotência no débito durante retry. \textit{Error}: estado inconsistente do saldo (decrementado duas vezes). \textit{Failure}: cobrança duplicada entregue ao cliente.
  \item Idempotência com \textit{idempotency key}: antes de debitar, verificar se o \texttt{pedido\_id} já consta na tabela de deduplicação; se sim, retornar resultado anterior sem novo débito.
\end{enumerate}
\end{tcolorbox}
\fi

\section{Parte 2 --- Confiabilidade e Disponibilidade}

\questao[9]{3}
Um servidor operou continuamente por 60 dias. Nesse período, ocorreram 4 falhas. Os tempos de reparo foram: 2,0h; 1,0h; 3,0h; 0,5h.
\begin{enumerate}[label=\alph*)]
  \item Calcule o $\MTBF$ (em horas).
  \item Calcule o $\MTTR$.
  \item Calcule a disponibilidade $\A$.
  \item Estime o \textit{downtime} anual desse sistema.
\end{enumerate}

\ifgabarito
\begin{tcolorbox}[gabarito]
\begin{enumerate}[label=\alph*),nosep]
  \item $\MTTR = 6{,}5/4 = 1{,}625\,\text{h}$. Tempo operacional: $60{\times}24 - 6{,}5 = 1433{,}5\,\text{h}$. $\MTTF = 1433{,}5/4 = 358{,}375\,\text{h}$. $\MTBF = \MTTF + \MTTR = \mathbf{360\,\text{h}}$.
  \item $\MTTR = (2{,}0+1{,}0+3{,}0+0{,}5)/4 = \mathbf{1{,}625\,\text{h}}$.
  \item $\A = \MTTF/\MTBF = 358{,}375/360 \approx \mathbf{99{,}55\%}$.
  \item $\text{Downtime anual} \approx (1-0{,}9955)\times 8760 \approx \mathbf{39{,}4\,\text{h/ano}}$.
\end{enumerate}
\end{tcolorbox}
\fi

\vspace{8pt}

\questao[10]{4}
Considere dois sistemas reparáveis:
\begin{itemize}[nosep]
  \item Sistema P: $\MTBF = 800\,\text{h}$, $\MTTR = 16\,\text{h}$
  \item Sistema Q: $\MTBF = 200\,\text{h}$, $\MTTR = 1\,\text{h}$
\end{itemize}
\begin{enumerate}[label=\alph*)]
  \item Calcule a disponibilidade de cada sistema.
  \item Qual sistema é mais \textbf{confiável}? E qual é mais \textbf{disponível}?
  \item Explique, em termos práticos, por que confiabilidade e disponibilidade podem apontar para sistemas diferentes.
\end{enumerate}

\ifgabarito
\begin{tcolorbox}[gabarito]
\begin{enumerate}[label=\alph*),nosep]
  \item P: $\A = 800/(800+16) \approx \mathbf{98{,}0\%}$; \quad Q: $\A = 200/(200+1) \approx \mathbf{99{,}5\%}$.
  \item Mais \textbf{confiável}: P ($\MTBF = 800\,\text{h}$); mais \textbf{disponível}: Q ($\A \approx 99{,}5\%$).
  \item Um sistema pode falhar com frequência, mas ser reparado rapidamente (alta disponibilidade, baixa confiabilidade). Outro falha raramente, porém demora muito para ser restaurado (alta confiabilidade, disponibilidade moderada).
\end{enumerate}
\end{tcolorbox}
\fi

\vspace{8pt}

\questao[8]{5}
Assumindo o modelo exponencial de falhas com $\MTBF = 1000\,\text{h}$:
\begin{enumerate}[label=\alph*)]
  \item Qual a taxa de falha $\lambda$?
  \item Calcule $\R(200)$, ou seja, a probabilidade de operar sem falha por 200 horas.
  \item Calcule $\R(1000)$.
  \item Se a missão exige confiabilidade de pelo menos 95\% em 100 horas, esse sistema atende?
\end{enumerate}

\ifgabarito
\begin{tcolorbox}[gabarito]
\begin{enumerate}[label=\alph*),nosep]
  \item $\lambda = 1/1000 = \mathbf{0{,}001\,\text{falhas/h}}$.
  \item $\R(200) = e^{-0{,}2} \approx \mathbf{81{,}9\%}$.
  \item $\R(1000) = e^{-1} \approx \mathbf{36{,}8\%}$.
  \item $\R(100) = e^{-0{,}1} \approx 90{,}5\% < 95\%$ \textbf{--- não atende}.
\end{enumerate}
\end{tcolorbox}
\fi

\vspace{8pt}

\questao[8]{6}
Uma empresa deseja garantir um SLA de $\A \geq 99{,}9\%$ para sua plataforma. O sistema atual tem $\MTBF = 500\,\text{h}$.
\begin{enumerate}[label=\alph*)]
  \item Qual deve ser o $\MTTR$ máximo para atender esse SLA?
  \item Com esse $\MTTR$ máximo, estime o \textit{downtime} anual permitido.
  \item Se na prática o $\MTTR = 2\,\text{h}$, o SLA é atendido? Justifique.
\end{enumerate}

\ifgabarito
\begin{tcolorbox}[gabarito]
\begin{enumerate}[label=\alph*),nosep]
  \item $500/(500+\MTTR) \geq 0{,}999 \Rightarrow \MTTR \leq 0{,}5/0{,}999 \approx \mathbf{0{,}5\,\text{h}}$ (30 min).
  \item Downtime anual permitido: $0{,}001 \times 8760 \approx \mathbf{8{,}76\,\text{h/ano}}$.
  \item $\A = 500/502 \approx 99{,}60\% < 99{,}9\%$ --- \textbf{SLA não atendido}.
\end{enumerate}
\end{tcolorbox}
\fi

\vspace{8pt}

\questao[10]{7} Indique \textbf{V} (verdadeiro) ou \textbf{F} (falso) para cada afirmação sobre $\MTTF$ e $\MTBF$:
\begin{enumerate}[label=\upshape(\hspace{0.7em})]
  \item O $\MTTF$ é utilizado em sistemas não reparáveis, enquanto o $\MTBF$ é a métrica adequada para sistemas reparáveis.
  \item $\MTBF = \MTTF$, pois ambos medem o tempo médio até a primeira falha do sistema.
  \item Para um disco rígido de servidor que pode ser substituído, o $\MTBF$ é a métrica mais apropriada.
  \item Um $\MTBF$ alto implica necessariamente alta disponibilidade, independentemente do valor do $\MTTR$.
\end{enumerate}

\ifgabarito
\begin{tcolorbox}[gabarito]
(1)~\textbf{V} \quad (2)~\textbf{F} \quad (3)~\textbf{V} \quad (4)~\textbf{F}

\smallskip
(2)~$\MTBF = \MTTF + \MTTR$; são distintos para sistemas reparáveis.
(4)~$\A = \MTBF/(\MTBF+\MTTR)$; um $\MTTR$ alto pode manter $\A$ baixa mesmo com $\MTBF$ elevado (cf.\ Ex.\ 10, sistema P com $\A \approx 98\%$ apesar de $\MTBF = 800\,\text{h}$).
\end{tcolorbox}
\fi

\vspace{8pt}

\questao[11]{8}
Um sistema deve operar continuamente por 48 horas para uma missão crítica. Duas opções estão disponíveis:
\begin{itemize}[nosep]
  \item Opção A: $\MTBF = 400\,\text{h}$
  \item Opção B: $\MTBF = 1200\,\text{h}$
\end{itemize}
\begin{enumerate}[label=\alph*)]
  \item Calcule $\R(48)$ para cada opção (modelo exponencial).
  \item Qual o ganho em pontos percentuais de confiabilidade da opção B sobre a opção A?
  \item Se o custo da opção B é 3$\times$ maior, você recomendaria a troca? Justifique considerando o contexto de missão crítica.
\end{enumerate}

\ifgabarito
\begin{tcolorbox}[gabarito]
\begin{enumerate}[label=\alph*),nosep]
  \item $\R_A(48) = e^{-48/400} = e^{-0{,}12} \approx \mathbf{88{,}7\%}$; \quad $\R_B(48) = e^{-48/1200} = e^{-0{,}04} \approx \mathbf{96{,}1\%}$.
  \item Ganho: $96{,}1 - 88{,}7 = \mathbf{7{,}4}$ pontos percentuais.
  \item \textbf{Sim, recomenda-se B}: em missão crítica, 7,4 p.p. adicionais de confiabilidade podem evitar falhas cujo custo humano ou operacional supera em muito o custo 3$\times$ maior do componente.
\end{enumerate}
\end{tcolorbox}
\fi

\section{Parte 3 --- Safety, Security e Resiliência}

\questao[12]{9} Marque a alternativa que diferencia corretamente \textit{safety} e \textit{security} no contexto de dependabilidade:
\begin{enumerate}[label=(\Alph*)]
  \item \textit{Safety} refere-se à proteção contra ameaças intencionais de agentes externos; \textit{security} trata de falhas acidentais que podem causar danos ao ambiente.
  \item \textit{Safety} preocupa-se com a proteção do ambiente contra consequências catastróficas de falhas acidentais do sistema; \textit{security} protege o sistema contra ameaças e ações maliciosas intencionais.
  \item \textit{Safety} e \textit{security} são sinônimos no contexto de dependabilidade, ambos referindo-se à ausência de consequências catastróficas.
  \item \textit{Security} é um subconjunto de \textit{safety}, pois toda vulnerabilidade de segurança representa também um risco de safety.
\end{enumerate}

\ifgabarito
\begin{tcolorbox}[gabarito]
Alternativa \textbf{(B)}. A diferença central é a origem da ameaça: \textit{safety} trata de falhas \emph{acidentais} (ex.: bug, falha de hardware) que podem causar danos físicos; \textit{security} trata de ameaças \emph{intencionais} (ex.: atacante, malware). As alternativas A e C invertem ou igualam os conceitos; D é incorreta porque a relação não é de subconjunto.
\end{tcolorbox}
\fi

\vspace{8pt}

\questao[8]{10}
Considere um sistema de controle de tráfego ferroviário. Um atacante compromete a rede de comunicação e injeta comandos falsos de sinalização.
\begin{enumerate}[label=\alph*)]
  \item Esse cenário é primariamente um problema de \textit{safety} ou de \textit{security}? Justifique.
  \item Explique como uma vulnerabilidade de \textit{security} pode se tornar um risco de \textit{safety}.
  \item Proponha pelo menos duas mitigações que enderecem tanto o aspecto de safety quanto o de security.
\end{enumerate}

\ifgabarito
\begin{tcolorbox}[gabarito]
\begin{enumerate}[label=\alph*),nosep]
  \item Primariamente \textbf{security} (ameaça intencional de um atacante), com consequência direta de \textbf{safety} (risco de colisão ou descarrilamento).
  \item A vulnerabilidade de security permite injeção de comandos falsos $\rightarrow$ o sistema de controle recebe informações incorretas $\rightarrow$ decisão errada de sinalização $\rightarrow$ acidente físico.
  \item Autenticação mútua entre nós de sinalização (certificados digitais) + watchdog de segurança independente que valida coerência dos comandos recebidos em relação ao estado físico dos trilhos.
\end{enumerate}
\end{tcolorbox}
\fi

\vspace{8pt}

\questao[9]{11}
Explique o conceito de \textit{hazard} e diferencie-o de \textit{failure}. Em seguida, para um sistema de piloto automático de drone de entrega, identifique:
\begin{enumerate}[label=\alph*)]
  \item Dois possíveis \textit{hazards}.
  \item Para cada hazard, uma \textit{safety constraint} (restrição de segurança funcional).
  \item Uma mitigação arquitetural para cada hazard.
\end{enumerate}

\ifgabarito
\begin{tcolorbox}[gabarito]
\textit{Hazard}: condição do sistema ou ambiente que pode levar a um acidente (dano físico). Diferente de \textit{failure}: um hazard pode existir sem causar acidente se as condições não se combinarem; uma failure é o serviço incorreto entregue.
\begin{enumerate}[label=\alph*),nosep]
  \item (i)~Perda de sinal GPS em área urbana; (ii)~Falha no sensor de altitude.
  \item SC(i): o drone não deve voar acima da altitude máxima sem confirmação de altitude válida; SC(ii): em caso de leitura de altitude inconsistente, iniciar procedimento de pouso de emergência imediatamente.
  \item Mit.(i): fusão de GPS + inercial (IMU) com detecção automática de falha de GPS; Mit.(ii): dois sensores de altitude independentes com votação majoritária (2-of-3 voting).
\end{enumerate}
\end{tcolorbox}
\fi

\vspace{8pt}

\questao[11]{12} Indique \textbf{V} (verdadeiro) ou \textbf{F} (falso) para cada afirmação sobre as propriedades CIA e AAA:
\begin{enumerate}[label=\upshape(\hspace{0.7em})]
  \item Confidencialidade (CIA) é violada quando dados de pacientes são acessados por pessoal não autorizado de outro setor hospitalar.
  \item Integridade (CIA) refere-se à disponibilidade contínua do sistema de prontuário, garantindo acesso ininterrupto 24 horas por dia.
  \item Disponibilidade (CIA) é violada quando um ataque de negação de serviço (DoS) torna o sistema de prontuário inacessível.
  \item Autenticação (AAA) determina quais recursos e operações um usuário já identificado pode executar no sistema.
  \item Accountability (AAA) permite rastrear quem acessou ou modificou um prontuário eletrônico e em que momento.
\end{enumerate}

\ifgabarito
\begin{tcolorbox}[gabarito]
(1)~\textbf{V} \quad (2)~\textbf{F} \quad (3)~\textbf{V} \quad (4)~\textbf{F} \quad (5)~\textbf{V}

\smallskip
(2)~\textbf{Integridade} garante que os dados não foram alterados indevidamente; disponibilidade contínua é a propriedade \textit{Availability}.
(4)~\textbf{Autenticação} verifica \textit{quem} é o usuário; \textit{Autorização} (não autenticação) define o que o usuário autenticado pode acessar.
\end{tcolorbox}
\fi

\vspace{8pt}

\questao[5]{13}
Explique por que projetar safety e security separadamente pode ser arriscado. Dê um exemplo concreto em que uma mitigação de security cria um novo risco de safety (ou vice-versa).

\ifgabarito
\begin{tcolorbox}[gabarito]
Projetar separadamente ignora interações entre as duas propriedades: uma solução que melhora security pode criar gargalos ou pontos de falha que comprometem safety, e vice-versa.

\textbf{Exemplo}: um painel de controle industrial exige autenticação multifator para todos os comandos (security). Em uma emergência real, o delay ou falha da autenticação impede o acionamento imediato do desligamento de segurança (safety), podendo agravar o acidente. Solução: projetar um \textit{safety override} autenticado por canal físico independente.
\end{tcolorbox}
\fi

\questao[9]{17}
Uma função recebe três inteiros representando os lados de um triângulo e classifica-o como equilátero, isósceles, escaleno ou erro (não forma triângulo). Sabe-se que a implementação contém o seguinte defeito: a condição de desigualdade triangular usa $\geq$ em vez de $>$ (ou seja, $a + b \geq c$ em vez de $a + b > c$).
\begin{enumerate}[label=\alph*)]
  \item Qual caso de teste detecta esse defeito? Forneça valores concretos.
  \item Explique por que um caso de teste com valores ``genéricos'' (ex.: $a=3, b=4, c=5$) \textbf{não} detectaria esse defeito.
  \item Qual técnica de teste (particionamento ou valor limite) é mais eficaz para encontrar esse tipo de bug?
\end{enumerate}

\ifgabarito
\begin{tcolorbox}[gabarito]
\begin{enumerate}[label=\alph*),nosep]
  \item CT: $a=3, b=4, c=7$. Com $\geq$: $3+4 \geq 7$ (verdadeiro $\to$ aceita como triângulo, incorreto). Com $>$: $3+4 \not> 7$ (falso $\to$ retorna erro, correto). O CT detecta o defeito.
  \item $a=3,b=4,c=5$: $3+4=7 > 5$ --- ambas as condições ($>$ e $\geq$) produzem o mesmo resultado (aceita), portanto o bug não é exercido.
  \item \textbf{Valor limite} (\textit{boundary value analysis}): o defeito reside exatamente na fronteira da desigualdade triangular ($a+b = c$).
\end{enumerate}
\end{tcolorbox}
\fi
